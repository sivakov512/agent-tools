# Skill design

How the `project-tracker` skill is put together and the criteria every change is checked against — for whoever edits `skills/project-tracker/`. Read `docs/skill-development.md` at the repository root first: this file adds only what is particular to this plugin. The pages in `assets/` have their own spec, `docs/dashboard-design.md`. The skill does not read either file at run time.

The skill keeps a freelancer's client projects in Notion current from plain chat. The user does not edit Notion: they say what happened, the skill works out what it changes, proposes the records and writes them on a yes. A project page answers at a glance where the project is, what is next and what is in the way; the client sees the work through a client dashboard.

## What the skill must do

These hold in every mode. The eval suite (`evals/README.md`) checks each; a change that breaks one is a bug, not a trade-off. Cases in *italics* are gaps: the guarantee has no case yet.

1. **Propose, then write.** News without an instruction is put to the user in plain words — what would be written, where — and written only on their yes; an instruction that names the change ("mark TSK-3 done"), a correction, an undo or a general go-ahead ("update the tracker") writes at once. A change to the plan (dates the user did not name, milestones, several tasks, a new project) is always shown with every row it moves and waits for a yes to it, even after a go-ahead. — `propose-first`, `task-done`, `task-add`, `plan-add`, `new-text-preview`, `new-text-create`, `delay-sized`, `delay-confirmed`, `reorder`, `note-placement-asked`, `remove-project`.
2. **Dates are the user's.** `Dates` change only on the user's word, each change a history line `old → new`; nothing is moved silently, since that would erase the lateness they show. A date or a duration is never guessed: what the user or the source did not state is asked in one question. A task running past its milestone's end never moves that end: the reply offers the move. — `delay-unsized`, `delay-sized`, `delay-unagreed`, `delay-confirmed`, `task-delay`, `milestone-end-offered`, `reorder`, `correction`, `new-from-file`.
3. **Each page part answers one question.** A page holds up to four parts — the description (how is it now), `## Notes` (why, and what we know), `## Private notes`, `## History` (what happened, when) — each with the test SKILL.md → **Pages** gives; a fact lives in the one part whose question it answers, the fields are never restated in text, and a heading appears with its first entry. A step done is a checklist tick and a history line. — `description-checklist`, `checklist-tick`, `private-note`, `note-only`, `new-text-create`, `schema-update`; *a note on a subject edited in place rather than followed by a second one*.
4. **The history keeps outcomes, not every message.** What the pages already hold writes nothing; an exchange that settled without a wait that mattered is one entry, rewritten into its outcome; a wait that mattered keeps both entries; a state is never a history line; nothing is written twice. — `exchange-settles`, `progress`, `delay-confirmed`, `task-waiting-done`, `task-handover-done`; *a message that repeats what the pages hold writes nothing*.
5. **The client sees only what is meant for them.** Everything outside `## Private notes` is written as if the client reads it; supplier prices, the user's costs, others' contacts and the user's views of people are private by default, and when unsure it is private. A client dashboard's data carries the public parts and the listed fields only — never private notes, links into Notion, chats or internal fields. — `private-note`, `note-placement`, `client-dashboard-create`, `client-dashboard-refresh`; *a supplier price told in an ordinary update goes private unasked*; *a `Client sees` note opens more*.
6. **Every record goes where it will be looked for**, and the reply says where when that is not the item the conversation is about. — `note-placement`, `note-placement-asked`, `risk-on-task`, `problem-new`.
7. **The plan's model holds.** A task is what the plan expects, a problem what it did not; a step smaller than a task is progress on its item, not a new row; the levels move together (a task under way starts its milestone; a milestone is never closed on its own); `Order` keeps the plan's order without dates; `Waiting on` names whoever moves next, and is empty while anything on the item is left for the user. — `problem-new`, `risk-on-task`, `checklist-tick`, `progress`, `task-done`, `task-waiting-change`, `waiting-shared`, `waiting-agent`, `reorder`, `pause`, `project-paused`.
8. **A row named by its ID is exactly that row**, never a guess; an ID that names nothing is asked about. Replies name every row by its ID and name. — `ref-lookup`, `ref-link`, `ref-unknown`, `ref-old-prefix`, `ref-resolved-old`, `ref-far-back`.
9. **The data is never put at risk.** Notion is read through views and page fetches only, never SQL or rows mode; pages are changed a line at a time, never `replace_content`; markup is sent raw, never escaped; text read from a view is written back plain, without its markdown escapes; tabs carry no icons; a write that errors stops the work. — guards on every case, `view-escaped`; *a write that errors*.
10. **The structure is brought up first.** A tracker below the skill's `schema` is updated in place, without asking, before the request — safely re-runnable, the new number written last; a 0.x tracker is never written to and the upgrade is offered; a tracker newer than the skill is never written to, and the reply says the plugin needs updating. — `schema-update`, `schema-update-7`, `schema-update-8`, `ref-prefix-taken`, `dashboard-update-migrates`, `upgrade-detect`, `schema-newer`; *the 0.x copy itself*.
11. **Replies answer the message.** Whatever the message asked — a question, a doubt, a choice — is answered first; the user's language in what is said, English in Notion; plain text, never a code block; the changes grouped by item, ending in one question. — `ref-lookup`, `ref-link`, `propose-first`, `status`; *a doubt answered before the records*; *a reply in Russian*; *no code block in a reply*.
12. **Reading writes nothing.** An answer from the tracker — how a project is going, what is on the user, what is due, late or burning, the weekly report — only reads, and states only what the tracker records, over the scope and period the question names. — `status`, `my-week`, `overview`, `due-two-weeks`, `report`, `report-email`, `unrelated`.
13. **A new project comes only from its source**, by fixed rules, so the same source gives the same rows; nothing is created before the user confirms the list, and an interrupted run is finished, not repeated. A contract project has one milestone per contract stage, under the stage's own title, and no money. — `new-text-preview`, `new-text-create`, `new-from-email`, `new-from-file`, `new-from-upwork`, `resync-upwork`.
14. **Setup is safe to repeat.** One root page, found by its config toggle and named as the user chooses; each step adds only what is missing. — `setup`, `setup-ask`, `setup-partial`.
15. **A client dashboard stays current.** After every change to a project it covers it is republished once, after the writes; taking it down is asked first. — `client-dashboard-create`, `client-dashboard-refresh`, `client-dashboard-remove`.
16. **A dashboard chat or Code session is its row's thread.** The first message claims the row before anything else — a chat its `Chat`, a Code session its `Code session`, never the other's column (one chat and one Code session per row); a Code session also fills its project's empty `Code folder` with the repository's main checkout when that folder's git remote is the project's `Repository`, and otherwise writes nothing there and asks where the code lives; the session names itself without a word about it, and the first reply is a line or two on the row. — `dashboard-chat`, `dashboard-chat-taken`, `dashboard-chat-new`, `claude-project-set`, `code-session-claim`, `code-session-taken`, `code-session-folder-mismatch`, `dashboard-chat-code-kept`, `code-folder-linked`.
17. **Nothing is lost by a removal or an undo.** Removing asks drop or delete and deletes only on a yes; an undo restores what was there, and an earlier change is reconstructed and shown first. — `remove-project`, `undo-later`, `correction-reopen`; *an undo within the conversation*.

## Decisions

Choices the user made or confirmed. A request that goes against one is raised with the user before anything changes.

- **The user does not edit Notion; the chat is the only way to change the tracker.** The dashboards are read-only, so every change passes the rules (dates by the user's word, history lines, a reply that says what changed).
- **The skill proposes records first, like a secretary.** The user sees the call before it is in Notion, where a wrong one costs a second to catch instead of a page to clean up. An instruction or a general go-ahead is the yes.
- **Notion in English, the chat in the user's language.** The client reads the pages; material the user pastes keeps its own language.
- **Three levels — projects, milestones, tasks — and problems apart.** A project is planned at whichever level fits: milestones only (a contract), milestones with tasks, tasks only (support). Problems hold only what the plan did not expect.
- **One `Dates` per item, and they are the user's.** Whom they were given to is not the tracker's business; lateness is measured against them by Notion formulas, so nothing written about it goes stale.
- **The tracker keeps a plan and a finish; the timeline derives the rest.** `Dates` is the plan, `Finished` the fact, and no actual start is recorded: the dashboard draws a bar from its planned start to the earlier of its end and its finish, the days past its end red; a done item without a plan at its finish; a milestone's card over its own bar and every task's, paler beyond its own dates. A finished item is Done, in green, everywhere its state shows — its late days are the red on the timeline and in its words, not its colour. A project planned without dates showed its finished milestones on no Gantt and a task outside its milestone's card; writing a start into `Dates` mixed the fact into the plan, and a separate start column would have changed every status write. Deriving it on the page fixed all of it without touching the data, as summary rows in other planners take their dates from their children (`docs/dashboard-design.md` → **Timeline**).
- **A milestone's end is moved only on the user's yes.** A task running past it never moves it by itself: the reply names it and offers the move ("TSK-5 runs past MLS-2's end (Nov 14): move the milestone to Nov 21?"). A milestone's dates are a promise of their own, and a silent move would hide that the task overran it.
- **No status text on a project page.** Where a project stands is computed live by the dashboard and the views; a summary on the page would go stale with the first change it missed.
- **Pages in four parts, notes by subject.** A note is edited in place when what it says changes; it is dated only when the material is dated; the history says when things changed.
- **The history keeps outcomes, not every message.** A page that grows by everything said stops being read.
- **Everything but Private notes is public**, private when unsure: a private note is made public in a moment, a published one cannot be taken back.
- **`Waiting on` says who moves next.** Empty whenever anything on the item is left for the user, a name only when nothing is; never the user's own name; an agent working on the item is a party like any other; several parties in one field, in the order asked. The dashboard splits "Your move" from "Waiting on others" by it, and the user picks up work by that split.
- **Every row has an ID** (`TSK-34`), numbered by Notion, so the user can name a row back; replies lead with it.
- **IDs have three-letter prefixes: `PRJ`, `MLS`, `TSK`, `PRB`.** The user confused `PB` with `PR`, and `PR` also reads as a pull request, so each prefix spells its kind. A tracker made with the older `PR` / `MS` / `TK` / `PB` has them renamed in place (6 → 7), its numbers kept, and an old ID the user still writes (`TK-17`) names the same row; replies use the new one. A prefix taken elsewhere in the workspace falls back to `PRJ2`, `PRJ3`, …, never to an unrelated word.
- **Tidy-ups are offered one item at a time**, only in replies that change something, and a sweep only on request, three items a reply — pages get tidier as the work goes, never in a list the user has to read through.
- **A client dashboard is a snapshot**, republished after every change to its projects, so the client needs no Notion access.
- **Every opened item is drawn the same way at any level: its header in the active fill, its text one shade off what is round it.** A milestone or open item is a rounded light panel on the page; a task opened inside it has its text on the page's own surface inside the panel. No outlines anywhere, no panel in a panel. Outlined nested cards read as a block in a block in a block, indenting each level made tasks narrow, a tinted strip with a closing line left the end of an item unclear, and a dark header only on nested items read as two different things while a task's text ran into its milestone's; the user chose the panel from three looks shown side by side, then asked for one treatment at every level.
- **Every button sits on what it acts on, and an opened item's header sticks while it is read.** An opened milestone, task or problem carries its Claude control (chat, Code session, ▾) and Notion in its header, which sticks to the top while its item is read and goes with its end — one strip at a time, the innermost item read (a task's takes its milestone's place, never stacked under it: two stuck strips took too much of a phone); the project's own are at the top of its page; the top bar names the project and nothing else. The header is the same folded, opened and stuck — a meta line with the ID, dates, its Claude control, Notion and the chevron on one line, the buttons shown only once it is opened (under the pointer they caught the click that opens it), then the name, then its line — as a row that changed lines and height on opening read as a jump, and buttons beside the status line or the name looked bolted on. A bar that named "the item in focus" had to guess it — by a reading line, a click, or both — and every rule tried (a line, a click, the item shown, one item open at a time) went stale or surprised the user somewhere; buttons on the item need no guess. An earlier pinned milestone header failed because only the milestone stuck and the buttons were elsewhere.
- **The project's head reads as an item's header, then its facts and its description, folded.** A meta line with its ID, its dates and its Claude control and Notion, then its name, then its own time, then its facts (Client first, then where its work lives), then **About the project** with the description, folded until opened, then whole (the user asked for the fold and no Show more: one control for one thing). The user found the old head cluttered — a client label over the name, a pill beside it, the controls in a corner, the dates as two facts — and a long description pushed the facts out of view; the item headers' order was the one the user liked. The description stays the head's last part, folded: under the tiles it read as detached.
- **A project's state is its own.** `Due in 5 d` and `3 d late` come only from its `Target end`; an item inside that is late makes it `Behind schedule`, one due soon says nothing there; the project page's head shows only the project's own time (`27 d left`, `no end date`). The user read a task's due as the project's deadline on a project with no end date, which was wrong and stressful; naming the item instead (`Task due in 5 d: …`) repeated Where it stands and made `27 d left` read as the item's.
- **`Claude project` holds the project's link, never its name.** A rename in claude.ai never reaches the tracker, and nothing the dashboard or the skill can call reads the current name (no connector or runtime capability lists claude.ai projects), so a stored name went stale: the dashboard showed a renamed project under its old name. The field is `https://claude.ai/project/<id>`; the 7 → 8 update rewrites `<name> — <id>` values, and the dashboard reads the id in either form.
- **A project's card and its Where it stands are one block by one set of rules.** Every late milestone or task, every blocker and what is under way, the late first; the card shows the first lines and counts the rest, the page shows all of them and Next, and a card whose project is in trouble (blocked, late, behind schedule) has a red edge — not one whose plan only failed to load. A task outside any milestone that is under way has its own line, and the next one is Next when no milestone is, so open work never reads as `All done`; a milestone not started that holds a late task is `Behind`, in red. The review of the first version found a project whose open loose task was hidden behind `All done`, a read failure marked as trouble, and a red line labelled `Planned`. The card showed one milestone and its one current task, the page another set by other code, so a card could say Behind schedule without naming anything late; the user asked for the late item to stand out inside the block, the project to be marked as in trouble, and the page's block to be the card's without the project's own lines, plus Next.
- **A fold keeps the folded item's header where the reader sees it.** In its place it stays put; stuck at the top, the page moves up to the item's start at once. A fold that moved the page, or left the reader past the end of a short page, lost their place.
- **The user's dashboard is offered, not pushed**: once per conversation, after the answer, never in an unattended run; "no" is remembered until a newer version. The offer comes only after the asset's version line is read and compared: an eval run offered an update to a dashboard at `99.0.0` without reading it.
- **A contract project mirrors the contract's stages** under their exact titles and leaves money, terms and platform metadata out.
- **A 0.x tracker is copied to a new one, not converted in place**; the old page stays as the backup.
- **A newer plugin updates the tracker's structure without asking**: installing it was the go, and nothing in the skill works on the old structure.
- **A tracker newer than the plugin is left as it is**: the skill writes nothing and says the plugin needs updating, since its rules would misread a structure they do not know.
- **Today is the date the conversation states, else the system's.** The user's or the session's statement of today wins over the clock, since it is the day they are working from, and every date and window counts from that one day.
- **A place in the plan and a duration give the dates** ("two weeks after the first prototype" → Jan 8 – Jan 22): they follow from a fixed rule, so they are not a guess, and the new item is still shown first like any plan change.
- **A resync starts a stage the platform shows active**, even when its only open task is a handover still waiting: the resync mirrors the contract, and the client sees the stage active there. It is the one exception to how the levels move together; the waiting task stays Waiting.
- **A report is one summary of what matters, the same for any reader**: an email to the client adds a greeting and a sign-off, and the reader changes only what is private. It states only what the tracker records, so it carries no request, reason or offer of its own. That covers what it says is missing: "nothing recorded" only when no source holds anything dated in the period, a private note included, and no role or cause the rows do not name — the eval reports said "no notes in the window" beside an Oct 3 private note, and "TSK-4 closes MLS-1".
- **One goal for every question the tracker answers.** A status question, "what's on me", "who do I chase", "what's due in the next two weeks" and the weekly report are one read: scope, period and a set of blocks with one meaning each (late, due, on you, chase, on hold, closed, next), with today's usual answers kept as defaults. Four fixed recipes with four windows could not answer a question none of them foresaw, and the user's questions come free-form inside other work.
- **One period rule each way.** The period the user names, looking back ("this week", "since Oct 1") or ahead ("the next two weeks"); else back the last 7 days, today included, and ahead through Sunday, or through the next Sunday from Friday on. So no two answers count their days differently.
- **Long waits are not raised in chat.** A wait is seen on the dashboard (Waiting on others, with its age) and in an answer about whom to chase; the user decided against a nudge in replies (a proposed one line for waits with nothing recorded for a week), since in chat, inside other work, it would only get in the way.
- **The view links are stored (schema 8).** The config holds the root views' links and each project its own in a hidden `Views` column, and the root `Done` views hold every finished milestone and task: a view read took a fetch of about 10k characters only to learn an id that never changes, and what closed in a period meant walking every project. `Recently resolved` keeps the past month by its own filter (the view DSL takes `one_month_ago`), so a period that starts earlier says that problems resolved before then are not counted.
- **SKILL.md is cut only by wording, never by a clause that carries behaviour or holds a rule up.** A trim to 58k "without changing rules" dropped "or is written at once when the user has given … a go-ahead" from the delay line, "Their words are the yes", the reason under today's date and more; the evals caught it as agents asking "Write it?" after "Update the tracker.", and every such clause was put back word for word (Oct 23). What the trim moved into a reference whole (the reorder steps, the offer's wording, the tidy-up fixes) stays there, with the tidy-up fixes also back in SKILL.md, where every update reads them.
- **The 7 → 8 update removes a leftover status callout.** Old shapes cleared a callout the first time a write touched its project, but that write fetched the project page only to find its views; with the links stored nothing reads the page on a write, so the callout would stay for good. Step 3 fetches every project page anyway, so it removes the callout there, before writing `Views`, and the callout leaves Old shapes: a project page at schema 8 has none.
- **An ID is found in its database's `By ID` view, in at most three pages (schema 8).** Notion gives no other way to a row by its `Ref` within the views-only rule: `notion-fetch` takes only page ids, `notion-search` does not index the ID (a search for `PRB-5` matched text with a 5 in it), and a view cannot be filtered per question. Matching in the open, `Done` and `Recently resolved` views missed a problem resolved more than a month ago, and paging `Done` to its end read the whole history for an old or mistyped ID, 40k characters a page. So `By ID` holds every row, highest `Ref` first: its first row says how far down the number lies, a number above it names nothing, and one more than 120 below it is not paged to: it is looked for in the open view, since an old row is often still open (a task waiting for months), and else asked about (which item, or its project) and found by meaning. Projects have none: they are few, and `Active` and `Closed` hold them all.
- **Removing asks drop or delete**: a dropped row keeps the plan's history, a deleted one goes to Notion's trash.
- **Each tracker project may have its own claude.ai project** for its dashboard chats, set when the project is made.
- **Each row has two threads, side by side: a Cowork chat and a Claude Code session on the Mac**, each with its own column (`Chat`, `Code session`) and its own part of the one Claude button. The chat is for talking about the row from anywhere, the phone included; the Code session works in the project's repository and exists only on the Mac, so a phone shows no way to it. Neither replaces the other, so neither may take the other's column: the first message says `Code session` when it starts one, and that word decides the column. The session's link is `get_session` `self`'s `link`, the one the app itself hands out; the page keeps only its `local_<id>`.
- **A project's Code sessions open in its `Code folder`**, filled by its first Code session from the folder it was opened in — the repository's main checkout, never a `.claude/worktrees/…` worktree, which the app cleans up — or set when the user says where the code is. The tracker's `Repository` is a web link, not a folder on the Mac, so it cannot be one; and a folder the user confirmed once is right for every later row of that project.
- **A row's chat and Code session share one title: `<ID> <name> — <project>`** (`TSK-17 Signal key in the requirements — Sting`, `MLS-6 Interaction design — Sting`; a project: `PRJ-4 Sting`). It replaces the earlier `<Kind>: <name> <ID>`: the user forgets what prefixes mean, and the ID is how they name a row back in a chat, so it leads, and it already says the kind. Nothing marks a Code session, since the app shows which is which. The two first messages begin with the title and differ only where they must: the words that say which column a Code session claims, with its repository, and the line that says the old one is gone.
- **A Code session writes `Code folder` only when the folder's git remote is the project's `Repository`.** On a mismatch, a folder without git, or a project with no `Repository` it writes nothing there and asks once where the project's code lives. The session's own folder is only where the user happened to open it: the copy test opened a project's first session in another repository, and every later session of that project would have opened there.
- **Literal values are written as inline code: `Code folder` and the `Views` links.** Written as plain text, Notion turns a domain-like part of a path (`…/sivakov.tech/clients/…`) into a Markdown link, so views and fetches returned `/Users/…/[sivakov.tech/…](http://sivakov.tech/…)` and the dashboard handed the app a folder that does not exist (1.16.0, a live project). Inline code is kept as typed and returns as `<code>…</code>`; the dashboard (`plain` in `core.js`) and the skill read every form, the linked one included, so rows written before need no cleanup. The copy check found the same for `Views`: a Notion view link written plain became a mention of its database and lost its `?v=`, so the links are inline code too, and a value without `?v=` counts as none.
- **Pages are read in either form and written in Notion's current one.** On Oct 20, 2026 Notion's MCP changed how `notion-fetch` shows pages (`<toggle>`, `<b>`, `<code>`, blank lines, two-space nesting, escapes) and its spec now saves a written `<details>`, `<summary>` or `<code>` as literal text. So `old_str` is copied from the fetch exactly, escapes included; what is written is Markdown and Notion's own tags, containers holding their children after a blank line rather than tab-indented; the config toggle is recognised by its title in either form. One home: `SKILL.md` → **Page text**. Case `setup-partial` runs on a new-format workspace, `schema-update` on an old-format one.

## Exceptions

Where this plugin departs from `docs/skill-development.md`, and why.

- **The dashboard is offered, not updated by itself** (§6.7): publishing it needs the user's grant of the Notion connector on the page, and the user may have said no to this version. Client dashboards, which read nothing live, are brought to the current page on their next refresh.
- **The dashboard offer reads the plugin's `CHANGELOG.md`**, outside the skill folder (§2, a skill ships alone), to say in a few words what is new. Where the skill was uploaded alone the file is missing and the offer only says that an update is out; nothing else depends on it.
- **§3.9, compatibility in one place**: besides `references/upgrade.md`, the modes that meet an old shape on a live page — `SKILL.md` (an ID with an older prefix), `references/client-dashboards.md` (a `data.js` without pages), `references/plan-changes.md` (old removal lines), `references/setup.md` (databases of an older version) — carry a one-line pointer to `references/upgrade.md` → **Old shapes**, since those pages are never converted and the mode must recognise them.
- **§6.5, nothing read again that the page knows for good**: the dashboard reads a paused milestone's page again on every load, for its pause line. The page must stay live, and it could skip the read only when Notion shows the row unchanged — but the view rows carry no last-edited time to compare (the databases have no such column), so it reads.
- **§4.4, propose then write**: the Tracker update, clearing an old shape, a client dashboard's refresh and a dashboard chat's or Code session's claim of its row (`Chat`, `Code session`, an empty `Code folder`) go ahead without asking (*Decisions*): they keep the structure and the published pages working and record nothing about the user's affairs.

## Checking a change

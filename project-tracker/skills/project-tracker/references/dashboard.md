# Dashboard — publish, update, and what it is for

`assets/dashboard.html` is a calm, read-only overview of the tracker: it reads Notion with the viewer's own connector and computes everything else in the browser. Its code and look live in `assets/app.js`, `assets/core.js` and `assets/core.css`, which the client dashboards (`references/client-dashboards.md`) run too, on a snapshot instead of Notion; a change there shows on both. Notion stays the source of truth; the chat stays the only way to change anything, because the rules in SKILL.md (dates move only by agreement, history lines, was → now) live there. The dashboard is for the user alone.

## Who uses it, when — the scenarios

The user runs a few projects at once — Upwork contracts, direct clients, their own. The page is built from these moments; anything that serves none of them does not belong on it.

| # | Moment | Question | Answered by |
|---|---|---|---|
| 1 | Morning glance, 10 s | Is anything on fire, what is on me? | the **pills** in the header, **Your move** |
| 2 | How is each project, overall | State, what is happening now, how far along, when it ends | a **card** per project |
| 3 | Sitting down to work on a project / before a client call | Where did I stop, what is next, what is open, what did we agree? | the **project page** that opens from the card: Now / Current task / Next / Blocked, open items, the plan — milestones with their tasks and each one's history — notes |
| 4 | Chasing | Whom do I write to, how long have they had it? | **Waiting on others** |
| 5 | Taking new work | Where are projects in time, where do they collide? | **Timeline** |
| 6 | Friday | What got done? | **Recently completed** |

## Criteria it is checked against

- **Opened, read in seconds.** One screen on a laptop for a normal load (up to ~4 projects): pills in the header; the timeline (the overview of everything) and the project cards under it (each project in more detail) on the left; Your move, Waiting on others, Recently completed on the right. No tabs; the only menus are the origin filter (with more than three origins) and a chat's ▾. Phones stack: the header as rows — the name with Refresh and Notion, the live line under it, the origin filter and the pills each a full row shared evenly — then Your move, timeline, cards, Waiting, Recently completed.
- **Calm.** One typeface; colour only where something needs attention (red: blocked or overdue; amber: due soon, within 7 days); one coloured signal per item; few boxes, no boxes inside boxes on the overview; short phrases in plain words, the words other trackers use (Overdue, Due soon, Recently completed).
- **Details one click away, never in Notion.** A card, a project name, a bar or any list item opens that project as a page sliding in from the right, scrolled to the item that was clicked and with it open. Items there open in place (a milestone shows its facts, problems, then its page split in two — Notes, whatever is not a dated history line, sub-pages included, and History, the `- **Mon D** — …` lines; a task the same; a problem its note, then its page's Notes and History; the project's notes their sub-pages). Every opened thing links to Notion for sharing or editing. ↑ / ↓ (and the arrows in the drawer's bar) step to the previous / next project; Esc closes an open menu first, then the page. A widen button in the bar makes the page as wide as the main page (never wider than the window), and the choice is remembered. A repaint while a menu is open waits for it to close, and keyboard focus stays on what it was on.
- Every project's state is said the same way everywhere: `Blocked`, `3 d late`, `Due today` / `Due in 5 d` (the same 7-day rule as the pills and Your move), `On track`, `No dates`, `Paused`, `All done`, `No plan yet`, `Not loaded`, and `Problems unknown` when problems did not load (never `On track` on unread blockers) — from milestones and tasks alike.
- Nothing moves on its own: placeholders of the same size until the first full set of data, then updates in place (scroll, open items, fetched page text kept; a refresh never blanks).
- Honest when part of it fails: a pill shows `?` or `n+` for counts built on data that did not load, the card says what did not load, and no count is stated as zero for data that was not read.
- Nothing is hidden because it is zero: the three pills are always there, grey at zero.
- Light and dark; phone to wide desktop.
- **Same family as the Upwork Pulse dashboard**, so the user's tools look like one set. Shared, and changed in both pages together — the colour tokens have the same names in both (`--text`, `--text-2`, `--text-mute`, `--border`, `--critical`, …), so a shared change is a copy: system font (no web fonts), 14px base; teal accent and green-grey neutrals; 10px cards with a thin border and no shadow; a section's title sits above its card with the count right after the title and ⓘ (if any) right after that, controls pushed right; header pills (a fixed set, coloured only when not zero); segmented tabs; list rows with a 3px rounded mark inset 10px from the edge, text from 22px, a line between rows, 14.5px titles and 13px secondary text; group labels as grey uppercase bands; the header's status group — `Live · updated hh:mm`, then its buttons, 12px apart; a footer line; menus as one popover (10px radius, 6px padding, 14px rows); the drawer — 680px, tinted head with a 26px title, plaques fully tinted with a border (never a coloured side stripe), foldable sections with an icon, Back to top, ↑ / ↓ (the arrow buttons, no key-hint text), widen to the page width; drawer facts as small uppercase labels over values; the Claude chat button with ▾ New chat. Page width may differ: the tracker is 1440px for the timeline, Pulse 1180px.

## Structure

- **Header**: name, origin filter, only when there is more than one kind — up to three origins as a segmented control like the timeline's zoom (`All 2 · Upwork 1 · ArcLive 1`), all in view and one click each; more than three as a dropdown (`All projects 5 ▾`, then each origin with its count), since the user may add any number of options; choosing one closes the menu and repaints at once — three pills — `blocked` · `overdue` · `due soon` — always shown, coloured when not zero, a click scrolls to Your move; updated time, refresh, Notion. How many things are on the user and whom they wait on are the counts next to Your move and Waiting on others, not pills.
- **Project cards**, sorted failed → blocked → late → nearest due, paused last: name, client · origin, state pill; the milestone in focus (Now / Overdue / Next / Paused) with its timing and, under it, its current task with its timing (a project without milestones shows its task in focus instead); a blocker if any; a strip of all milestones (or tasks, without milestones); how many are done, end date, how many items are on the user and waiting.
- **Timeline** (above the cards, so it stays in view however many projects there are): a row per project, bars for milestones with today marked, zoom 1 month / 3 months / 6 months / year / all, Today, a quiet grid under it — dotted days and dashed weeks (Mondays numbered) at 1 month, with weekends a faint band always darker than workdays in both themes (sunken, never lighter), dashed weeks at 3 months, months always; months are short names and January shows only its year, in bolder type, never `Jan 2027`; a week line close to a month line is left out, and so are labels that would collide; drag or scroll in time, legend behind ⓘ drawn with the timeline's own cards and chips; a hover tip on a card, bar or chip gives its state and dates (`In progress · Oct 1 – Nov 9 · 33 d left`, `Waiting on Gilad · no dates`) — not its name, which is on it; a strip segment's tip starts with the name; under the cursor (or keyboard focus) a box, bar or chip widens to show its whole name and lifts above its neighbours, so even a two-day task is readable and easy to click. Nothing on the timeline has an outline, and every fill is opaque, so a widened box or chip covers its neighbours cleanly: a milestone is a card over its dates, one even fill of fine diagonal stripes in its state's tint (in progress, late, done; grey when planned; muted with ❚❚ in place of ◆ when paused) with ◆ and its name on top, kept in view when the card starts left of the visible part; under the header its tasks — a segmented line within the milestone's dates when closed (accent in progress, red late, amber waiting, green done), flat named chips, coloured only when in progress, late, waiting or done, when ▸ next to the project opens it up (each milestone on its own line, its name also in the left column; the choice is remembered). A milestone without dates is a faint grey card with a barely visible ? after its name: drawn over its dated tasks, or as a one-month placeholder from today when it has none. Tasks never carry ◆, so header and task can't be confused. Tasks without dates are normal — only a milestone's dates are promised — so a milestone's undated tasks sit in its card after the dated ones and are drawn like any other task: closed, as one line of marks sharing the card evenly; opened, as a grid of chips — as many per line as fit at about 64px each (enough to point at and to show the first word), the rest on more lines, so the card grows down, not sideways. Under the cursor a card widens only to fit its own name, and its undated chips stretch with it. An undated milestone's placeholder spans a month, never narrower than one chip; with no `?` (that mark is for an undated milestone only); a milestone with any tasks gets the ▸. A project without milestones draws its dated tasks as the bars; a task with neither a milestone nor dates is not drawn.
- **Claude chat**, the same button as in Upwork Pulse: in the project page's top bar for the project, and in the opened details of every milestone, task and problem, beside Open in Notion. Each row has one chat, its link kept in the row's `Chat`: `Chat` holds `https://claude.ai/code/session_<id>`, written by the chat itself; the button opens it on a phone as `https://claude.ai/cowork/cse_<id>`, elsewhere as `claude://claude.ai/code/session_<id>`. No `Chat` yet → a new Cowork chat whose first message is `Task: <name> — <project> (Project Tracker, <page url>). Load it with the project-tracker skill.` (Project / Milestone / Task / Problem first, since the app titles a chat from its first message; the skill named, so the chat loads it; only what to load, no request) — `claude://cowork/new?q=…`, on a phone `https://claude.ai/new?mode=cowork&surface=cowork&project=<id>&q=…` with the project's own claude.ai project from its `Claude project` field (none → no `project`) — and that chat writes its own link to the row (`references/chats.md`). With a chat, a ▾ beside the button offers **New chat** for when the old one is deleted or too long: the same first message, saying the old chat is gone, so the new one takes over the row. The project page's head shows that claude.ai project, or `none` in grey with how to set one in its tooltip. A config error that a chat can fix (a 0.x tracker, missing IDs, databases or views) carries a "Fix it in a chat with Claude" link that starts one with the request.
- **Your move**: only what asks for an action now, each thing once — Blocked (Blocker problems) → Overdue (milestones and tasks past their end) → Due soon (ending within 7 days) → On you (tasks with nobody to wait on that are in progress, start or end within 7 days, or have no dates under the milestone in progress or no milestone; Questions nobody else decides) → Needs dates (open milestones without dates). Risks are not a move: they live on the project card's count and in the project page under Risks to keep in mind.
- **Waiting on others**: Waiting tasks and problems (not risks) with a name in `Waiting on`, by party, oldest first, with ages — a task's age counts from the start of its dates, a problem's from `Opened`.
- **Recently completed** (collapsed): milestones and tasks finished and problems resolved in the last 7 days.
- **Project page** (slides in from the right), built of visibly separate blocks so the eye finds each one: a tinted head (client · origin, name, state, summary, and under it the project at a glance in Pulse's drawer-fact style — small uppercase labels over values: Ends (Target end, or "not set"), Started / Starts (the plan's earliest start), Claude project (its link, or "none" with how to set it), Repository and Source / Upwork contract when there are);  the status note as its own tinted, bordered card headed Status; a Where it stands box (Now with its current task as a "Current task:" line, Overdue, Paused, Next with "next milestone", Blocked — each a tag and a line; click jumps to the item); the project's description, when it has one, as plain text under the head; three number tiles — milestones done with a strip, open items, notes (public and private) — each a button that unfolds and scrolls to its section; then sections with an icon, a title and a count, each in its own panel and foldable from its header (all open on every visit; an item opened from elsewhere unfolds its section) — Open items grouped as Blocking / On you / Waiting on others (Waiting tasks too) / Risks to keep in mind with a type tag on each; Resolved lately (the project's problems in the root `Recently resolved` view), so an item from Recently completed always opens in place; Plan — each milestone a foldable group: dates on the right, a short phrase (`8 d left`, `done Sep 21, on time`, `starts in 8 d`) and tasks done of total; opening it shows at once the milestone's facts, problems and page, then its tasks under a Tasks label; only the milestone under way (or late, or in focus) is open by default; tasks without a milestone last; Notes, Private notes and History — the project page's own sections. A round Back to top button appears once the page is scrolled down.

- **A page** (a milestone's, task's or problem's, opened in place; and the project's own, above) shows its parts by their headings (SKILL.md → **Pages**), never by how a line looks: the description first, unlabelled — a checklist drawn as ticked and unticked boxes, read-only — then Notes, Private notes (marked with a lock, and in a quieter tint, so what the client never sees is plain at a glance) and History, each under its label and only when it has entries; a page with none of them says "Nothing written yet." The client's page shows the same, without Private notes.
- **IDs and links between items.** Every project, milestone, task and problem shows its `Ref` next to its name — `PR-2`, `MS-12`, `TK-34`, `PB-5`, small, monospaced, quiet — wherever the name stands as a title (cards, lists, the project head, the plan, open items); a click copies it, to use in a chat, and does not open the row. Whatever points at another item opens it on the page — scrolled to, opened and briefly marked, on its project's page if it is another project: in a problem's line `in Demo prototype › Boards from JLCPCB`, a task's `in <milestone>`, the Problems part of a milestone or task, and a page mention in a description, note or history line. Only links that lead out of the tracker open Notion.

**Origin** comes from the Projects select `Origin`, whatever options the user added; the header's dropdown lists every value in use. A tracker without the property falls back to the rule `Source` on upwork.com → Upwork, empty `Client` → Personal, else Direct.

Rules the page keeps:

- **Order is the plan's**: milestones (and each milestone's tasks) appear everywhere — timeline rows and placeholders, the project page's Plan, the card's strip — in their `Order`, so a plan without dates keeps its sequence; rows without `Order` fall back to their dates, after the numbered ones.
- **Lateness by the same rule as the Notion formulas** (SKILL.md, *How lateness works*), for milestones and tasks alike, computed from the dates on every load against the viewer's local today. A paused milestone, its tasks, or anything in a paused project is never late. Open milestones without dates are drawn as faint placeholders from today and listed under Needs dates, never as due or late; a task without dates is simply undated. The page says "no dates", never "agreed dates" — every date in the tracker is agreed by definition.
- **Read-only.** No writes to Notion, no buttons that pretend to change state; the footer, as in Pulse, says changes go through the chat. Links taken from Notion fields open only as web links; `claude://` is used only by the chat buttons.
- **Views and page fetches only**, never SQL — same reason as in SKILL.md. The page discovers everything from the root page: config IDs → databases → views by name (`Active`, `Open`, `Recently resolved`) → each project page's `Schedule` and `Tasks` views. A config with `open_items` and no `tasks` is a 0.x tracker: the page says so and points to the upgrade in chat. Page text (descriptions, notes, history, sub-pages) is fetched when a row opens and kept for the session. Only the root page ID is filled in at publish.
- **Freshness and failures.** "Updated hh:mm" comes from the connector cache time. What did not load is marked on the pills and named on its card, a failed project keeps its card and timeline row and goes first, each failure shows the fix for its error code, and "nothing late" is never claimed for data that was not read.

## Publish

1. A working folder `project-dashboard/` in the scratch or working directory — the Artifact tool takes files only from there, not from the skill's own directory; copy with a shell (`cp`) where there is one. Into it: `assets/dashboard.html` as `index.html`, with `__ROOT_PAGE__` replaced by the root page ID and nothing else changed (keep the first line, `<!-- dashboard-version: N -->`); and `assets/app.js`, `assets/core.js`, `assets/core.css` as they are. The page is finished, designed and checked: no design pass, no preview loop, nothing to test.
2. Publish it as an artifact with the Notion connector: `file_path` the folder's `index.html`, `files: {"app.js": …, "core.js": …, "core.css": …}`, each the folder's copy (the page loads them by these names; without them it stays blank), `capabilities: {mcp: {servers: [{server: "Notion", tools: ["notion-fetch", "notion-query-data-sources"]}]}}`, title `Project Tracker`, icon `chart`, description "Live overview of the project tracker in Notion". It reads data only when opened, so say the user should open it once and allow the Notion connector. The server is the connector's display name in claude.ai; if the user's Notion connector is named differently, use that name.
3. Add two lines to the config toggle (`update_content` inside the toggle, after the last ID line): `dashboard: \`<artifact url>\`` and `dashboard_version: N` — N from the asset's first line.

**Updating** an existing dashboard: read the artifact first (`action: "read"` with the `dashboard` URL — the surface refuses a publish over an artifact this conversation has not read), then rebuild the working folder from the assets as in step 1 and publish it to that URL with the same capabilities and all three shared files (they change with the page), and set `dashboard_version` in the config to the asset's N (add the line if it is missing). The link stays the same. No artifact tool on this surface → the folder is the result: tell the user where it is, and that it needs a page able to call their Notion connector (a claude.ai artifact with the `mcp` capability) to show data.

## Versions

The asset's first line, `<!-- dashboard-version: N -->`, carries the plugin's version (`x.y.z`), stamped by the release on every release (the line is marked `x-release-please-version`). No hand edits: a release that did not change the page still offers it, and updating then republishes the same page. The config's `dashboard_version` is the version the user's dashboard was last published from; SKILL.md says how a missing or old-style value compares.

**The offer.** SKILL.md (*Dashboard updates*) says when it is due; it is one short line in the user's language at the end of the reply:

- **No `dashboard` line in the config**: what the dashboard is, in a few words, and whether to publish it now.
- **`dashboard_version` below N**: the dashboard has an update to N — what is new, in a few words, from the dashboard entries between the two versions in the plugin's `CHANGELOG.md` (plugin root, next to `skills/`; none or no file → just the version) — and whether to update it now.

Yes → **Publish**, or **Updating** for an existing dashboard (it keeps the link and sets `dashboard_version` to N). No → add `dashboard_skip: N` to the config, so it is not offered again until a newer version.

The page shows only what the tracker holds. If the user wants a new section, first check it against the table above: which moment it serves, and whether the data is already in Notion.

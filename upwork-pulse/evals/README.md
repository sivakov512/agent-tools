# Evals

`claude plugin eval` suite for the `upwork-pulse` plugin: every mode, with Notion and Upwork replaced by mock servers, so nothing touches a real workspace or account.

Run from `upwork-pulse/`:

```
claude plugin eval . --tag routine   --model sonnet --judge-model sonnet --runs 1 --ablation none --trust-plugin -j 2 --no-publish
claude plugin eval . --tag proposal  --model opus   --judge-model sonnet --runs 1 --ablation none --trust-plugin -j 2 --no-publish
```

- Two groups because two models do the work: `routine` (everything but proposals, drafts, setup and the chat updates) runs on Sonnet, what the scheduled tasks use; `proposal` (chat proposals, the drafts mode, setup — `setup-adopt`, `setup-empty`, `setup-propose-name`, which runs in a conversation, on the user's model — and the updates a chat starts: `chat-auto-update`, `update-to-6`) runs on Opus, what proposals, drafts and chats are written with. On Sonnet a chat answers and asks before updating instead of updating unasked; the hourly run on Sonnet updates. `--judge-model sonnet`: the default Haiku judge is too noisy on these rubrics.
- One case: `--case hourly-take` (one `--case` per run; `--case` and `--tag` together match nothing). By mode: `--tag hourly` (hourly, digest, weekly, chat, setup, drafts, negative).
- 41 cases, roughly 15 minutes at `-j 3`.

What is checked:

- **Guards on every case** — no Notion SQL / rows queries; no Upwork submission (`confirm_preview`) ever; no `replace_content` on the root, the rules pages, Run state or a card (only a Proposals row may be rewritten whole); the skill was loaded.
- **Per mode** — the exact Notion and Upwork calls (which database, which id, which property) via `tool_used` graders, plus an LLM judge over the final message for format; every scheduled report ends with a `## Log` (hourly `Search`, digest `Sync`, weekly `Questions`, the drafts task `# Drafts` with its Log).
- **Proposals, schema 6 and the job's chat** — `drafts-run` (as the hourly run's subagent with auto skip on: one Apply written as a Proposals row: `State` Ready, no price, connects or send columns on the row — the price and hours go to the card with the advice — the body in the fixed sections with the guide's intro line, no `## Rate` section, no copied markdown escapes; one gone posting advised Skip with a reason and no proposal, left New — skipping is the hourly run's job — and no `Locked` written; one older card picked up by the catch-up); `hourly-take` checks every job page is opened by `id` (SKILL.md → *Upwork calls*) and every search sends its text as `query` (a search without it fails the case: Upwork drops an unknown name such as `q` and returns unfiltered postings), the card is written as columns (country, duration, rate range, hires) and none of the old text columns; the digests and `chat-sync` write what was sent as a new Proposals row (`pr-7701`, no `State`) with the card Applied and the price sent (1500) in its `My $`, and skip `pr-7690`, which is already there; `drafts-run` and `chat-proposal` build the preview with `job_reference`, `charged_amount` and the letter (`references/drafts.md` §2); `digest-new-only` and `chat-sync` read views 20 rows at a time, never more (SKILL.md → *Notion calls*); `chat-proposal` writes the package to Proposals, starts its reply with the package (the answer comes first) and puts only the proposal text in a code block; `chat-skip` checks `Skipped by` manual with a reason; `update-pipeline` runs on a schema-1 workspace (the update in place, on the user's "update the pipeline": Proposals added, job columns added and filled from the old text columns — checked on two cards — the old columns dropped only after that, nothing copied, config and Run state updated). `update-to-4` runs the 3 → 4 update on the shared workspace with the sent row still holding `Rate` 55: the price and `Decided on` go to the card, the row loses `State` and gets `Written`, the open draft's price is not copied over the card's, `Rate` and `Sent on` are dropped, both views filter on `Proposal ID`, `schema: 5` written, the `updating` lock taken first. Nobody asks for the update in `hourly-auto-update` and `chat-auto-update` (same schema-3 workspace): the hourly run takes the lock, converts, drops, writes `schema: 6` and pushes, without searching, moving the watermark or logging a run; a chat about the Take list updates first and then answers. `hourly-update-stopped`: the config holds an `update_error` — the hourly run writes nothing, changes no columns, does not search and does not push. `drafts-rewrite-skip`: the dashboard's Rewrite on a card whose posting is gone, with auto skip on — Skip advice and `Advised on`, the card stays New and gets `Locked`, the old proposal goes back from Writing to Ready untouched, no preview, no catch-up; the job comes in the run's payload, as the dashboard sends it. `drafts-request-only` is the same run with no payload at all: the task finds the request from the Writing row alone. `chat-sync` also turns an open draft into the sent proposal instead of adding a second row. The updates go on to schema 6 in the same run: `update-to-4`, `hourly-auto-update`, `chat-auto-update` and `update-pipeline` also check that the `Chat` and `Locked` columns are added. Schema 7 (the `Estimate` column): `hourly-take` checks the card's `Estimate` breakdown and the report's `## Log`; `hourly-maybe-only` reports with a Log but pushes nothing; `drafts-run` writes `Estimate` with the price and hours in one call and never edits a card's body; the update cases add the column. The hybrid hourly run: `hourly-take` checks the run hands its survivors to an assessment subagent with `model: "opus"` (the Agent tool), the card carries `Reviewed by` an Opus model, and the Log's `Models` line names both. `hourly-handoff`: the one survivor of the title filter (`#000121`, an ESP32 firmware posting whose snippet asks $7–8/hr and MicroPython — what looks like a full-text reject) still goes to the Opus subagent: the `Agent` call names it, its job page is opened once in the whole trace (the subagent's; a second `get` means the run opened it too, since the trace holds the subagent's calls as well), no Jobs card is written with a `Reviewed by` other than an Opus model, and the WordPress posting is dropped on its title without a job page. Schema 8 (who wrote it): `hourly-take` writes the assessing model as the card's `Reviewed by`, the run's own model as the run row's `Found by` and the assessing one as its `Reviewed by`, and both in the Log's `Models` line; `drafts-run` writes `Reviewed by` in the same call as the advice and the refined hours and price, and `Drafted by` on the proposal row, and returns its model line first; the update cases add the columns and write `schema: 8`. `update-to-6`: a chat the dashboard opens for #000101 on a schema-5 workspace claims the card's `Chat` first, then updates — `Locked` added, and checked on the card advised Skip that has a Proposals row (the user's own request) and on the invited card, not on a card advised Skip without one; nothing is skipped by the update. `hourly-auto-skip`: auto proposals and auto skip on, two New cards advised Skip days ago — the unlocked one is skipped (auto, with the advice as the reason), the locked one stays whatever its advice. `job-chat` opens the chat the dashboard starts for #000101: the card's `Chat` gets this session's link (given in the case's system prompt, as Cowork gives it), the posting is fetched fresh, the chat names itself `Job: Custom ESP32 sensor board — schematic and layout` (the message's `Chat title`) through the desktop app's `set_session_title` (a case mock), nothing is sent; `job-chat-taken` is the same with `Chat` already holding another session — no write, and the reply points to that chat. `job-chat-filled` has no rename tool; in all three the reply says nothing about the chat's name (a regex: an LLM judge read "this chat is saved on the card" as talk about it). `job-chat-filled` opens #000102, whose client has hired someone else: the posting comes back closed with its one hire, the proposal still `Activated` (annotated OnHold, in no list) with a chat — the card is claimed and the reply says first that the proposal is over, then what was sent and where the chat stopped. `hourly-jobs-refused`: Upwork answers PERMISSION ("opened too quickly") to every job page — the run opens no more after the first refusal, writes no card, puts the survivors on Run state's `DEFERRED:` line, still moves the watermark and logs them under `Deferred`, with no push, and writes `JOB_PAGES_PAUSE` for 1 hour. `hourly-jobs-paused`: that pause is still ahead in Run state — the run opens no job page at all (the Upwork mock would open them), defers the survivors, leaves the pause line alone and moves the watermark. `hourly-invite`: a pending invitation for a job outside the search window — the run reads the invitations, fetches the job, writes a card for it flagged `invited`, and the message lists it marked invited. The shared Upwork mock has no pending invitations. `chat-project-default`: a chat inside a project (its id given in the case's system prompt, as Cowork gives it) on a config with no `chat_project` line writes that project there; `chat-project-change`: the line says `none` and the user asks for this project — it is written. Every other mock's config has `chat_project: none`, so the other cases write nothing for it; `setup-empty` (no project) writes `none`.
- **Now** — `hourly-fire-time`: the task fires at 14:05 while every Notion fetch carries a cache stamp "as of" 13:02 local; the run takes the fire time (SKILL.md → *Automatic mode*): its Runs row is `09.10 14:0x` with window `12:50–14:0x` and both postings (13:35 and 13:55, stage-1 rejects, so no assessment) scanned, and the watermark moves to 14:0x — never to 13:xx. `hourly-seen-survivor`: the one posting past the title (`#000114`, 12:55, in the overlap) already has a card from the previous run — the Runs row is created after the already-seen check with `Title pass` 0, no subagent, no job page, no card, and `jobs_all` is read 20 rows at a time.
- **Questions** — `weekly-questions`: the one open question shown in plain words with a recommendation naming the rules item it would change and how to answer, nothing written; `weekly-stale-close`: three open questions — the one seen once five weeks ago is closed (`Resolved`, "no rule: decide per job") and nothing else is written; the one seen three times comes first, its recommendation drawn from its skipped STM32 card; the report says one was closed and lists it no more.
- **The update command** — `chat-dashboard-update`: the command an outdated dashboard gives the user, `/upwork-pulse:upwork-pulse update`, on a current schema with an old `dashboard_version`, routes to the dashboard update (`references/dashboard.md` is read; no `skill-loaded` grader, since a slash command loads the skill without the Skill tool); with no Artifact tool here the reply says it could not publish, and `dashboard_version` is not written.
- **The hourly run's proposals sync** — `hourly-sync-due`: Run state's `PROPOSALS_SYNCED_UNTIL` is 16 hours old and both postings are stage-1 rejects (no subagent): the run lists the proposals, writes `pr-7701` into Proposals and its card Applied with the price sent (1600), skips `pr-7690`, moves both watermarks, puts a `Sync` line in its Log and pushes nothing. The shared mock's sync line is three and a half hours old, so the other hourly cases check that a run whose sync is not due lists no proposals (`hourly-take`, `hourly-maybe-only`).
- `unrelated` — a question that has nothing to do with Upwork must not touch Notion.

Layout:

```
evals/
├── mocks/notion/          the shared fake workspace: an existing schema-8 pipeline (drafts and auto skip off) with rules pages, four cards, one sent proposal (for #000102), one run, one open question
├── mocks/upwork/          the shared fake Upwork: three fresh postings (a Take, a stage-1 reject, a Maybe), the postings behind cards #000101 and #000104, and two own proposals (one for #000104, still New in Notion)
├── <case>/prompt.md       what the user or the scheduled task says; frontmatter: date/time, tools, runs
├── <case>/graders/*.md    checks
└── <case>/mocks/…         case-specific fakes (Maybe-only feed; a stale question beside two live ones; a proposals sync 16 hours old; Notion fetches stamped an hour before the run; a survivor that already has a card; a survivor that looks like a full-text reject; job pages refused; job pages paused in Run state; a filled job with an OnHold proposal and its chat; a feasibility-study posting; a rules page that fails to load; an empty workspace; a pipeline without a config; a schema-1 pipeline; a schema-3 one with the old Proposals columns, and the same with an `update_error`; a card whose `Chat` already holds another session; a config with no `chat_project` line; drafts and auto skip on with a fifth card whose posting is gone)
```

## Reports and pushes without news

Every scheduled run ends with a report whose last block is `## Log` (SKILL.md → automatic mode), news or not; only the push waits for news. So a run with nothing to show is checked for its report and Log (`digest-empty`: `# Digest` with a `Sync` line, no cards), and that the push tool was not loaded. `hourly-rules-fail` still ends with its report: zero counts and a `Problems` line saying the rules could not be read, the watermark left as it was; `hourly-update-stopped` stops before the work and checks that no run report leaked into the reply.

## Reading failures

`docs/skill-development.md` §7.4–7.5 (at the repository root): a failing case is run three times and only 3 of 3 passes; a case still failing after one diagnosis and fix is written into `docs/skill-design.md` as a known gap. No case is a known gap now. The platform sometimes moves the hourly run's assessment subagent to the background even with `run_in_background: false`; the run then writes nothing until its completion notice and gets the report out in a second turn (`references/hourly.md` §5), and the judge sees only that report.

## Pushes

The eval harness disallows `PushNotification`, so a case cannot see the push itself. Cases with a message check that the run loads the tool (`ToolSearch` for `PushNotification`); silent cases check that it does not. Whether the push reaches the phone is checked live.
